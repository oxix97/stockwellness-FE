# 프론트엔드 UI 품질 검증

## 개요

하나의 정상 화면 캡처가 아니라 전체 사용자 동작을 검증한다. 모바일 웹, 상태 범위, 접근성과 정확한 금융 정보 표시는 출시 필수 조건이다.

## 검증 절차

1. `AGENTS.md`, 정확한 후보 빌드 또는 diff와 관련 구현·테스트를 읽는다. 반응형 기준은 `docs/responsive-ui.md`, 버전·명령은 `package.json`에서 확인한다. 존재할 때만 `../docs/design/`, `../docs/specs/`의 화면 계약을 읽고, 없으면 추측하지 않고 검증 공백으로 기록한다.
2. 테스트한 라우트, 계정 상태, 데이터 조건, 뷰포트, 브라우저와 빌드 식별자를 명시한다. 후보를 식별할 수 없으면 출시 판정을 내리지 않는다.
3. 다음 상태 매트릭스를 확인한다.
   - 로딩과 지연 응답
   - 빈 상태 또는 최초 사용 상태
   - 현실적인 최소·최대 콘텐츠의 성공 상태
   - 복구 가능한 API 오류와 복구 불가능한 API 오류
   - 미인증 또는 만료된 세션
   - 서버 데이터의 오래된 상태와 재조회 동작
4. 관련되는 경우 0, 양수, 음수, 누락 값, 긴 값, 소수점, 단위, 반올림, 통화, 기준일과 EOD 표현을 확인한다.
5. 360×800 같은 좁은 뷰포트에서 모바일을 먼저 확인한 뒤 일반 휴대전화 너비와 데스크톱을 확인한다. 넘침, 고정 내비게이션, 시트, 키보드 겹침, 안전 여백, 회전 영향을 받는 레이아웃과 터치 영역을 점검한다.
6. 키보드 순서, 보이는 포커스, 의미 있는 이름, 제목, 레이블, 대비, 모션 감소와 색상 이외의 정보 전달 등 상호작용과 접근성을 확인한다.
7. 컨트롤 클릭만이 아니라 최종 이동 결과까지 확인한다. 로딩·실패 안내에 원시 API 오류가 노출되지 않는지 확인한다.
8. 기존 Vitest와 Playwright 증거가 인수 조건을 직접 검증할 때 활용한다. 핵심 증거가 없으면 가장 좁고 안전한 테스트 명령으로 재현한다.
9. 사용자가 수정을 별도로 요청하지 않으면 QA는 읽기 전용으로 수행한다.

## 발견 사항 형식

발견 사항을 먼저 보고하며 각 항목에 다음을 포함한다.

1. 심각도: `차단`, `중요`, `경미`
2. 라우트·컴포넌트와 상태
3. 뷰포트와 재현 절차
4. 기대 결과와 실제 결과
5. 사용자 또는 금융 의사결정에 미치는 영향
6. 증거 위치

마지막에는 다음 중 하나로 판정한다.

- **통과** — 필수 상태와 모바일 흐름에 증거가 있고 차단 문제가 없다.
- **조건부 통과** — 승인된 비핵심 후속 작업만 담당자와 함께 남았다.
- **실패** — 필수 상태가 실패했거나 모바일, 금융, 접근성 또는 빌드 증거가 없다.

## 최소 증거 매트릭스

| 영역 | 필수 증거 |
|---|---|
| 반응형 UI | 좁은 모바일과 데스크톱 결과 |
| 데이터 상태 | 로딩, 빈 상태, 오류, 성공 |
| 금융 값 | 0, 음수, 누락 값, 단위·날짜 의미 |
| 상호작용 | 진입 동작부터 최종 결과까지 |
| 접근성 | 키보드, 포커스, 이름·레이블, 색상 외 단서 |

## 흔한 실수

- 하나의 화면 캡처나 뷰포트만 보고 출시 가능으로 판단한다.
- “관찰되지 않음”을 결함이 없다는 증거로 기록한다.
- 사용자 정의 컨트롤의 키보드, 포커스 또는 스크린 리더 이름을 무시한다.
- API 오류를 사용자에게 적절한 문구로 간주한다.
- 금융 값의 기준일과 부호를 빠뜨린다.
